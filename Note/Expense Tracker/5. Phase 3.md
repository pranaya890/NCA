Yes. At this point, **Phase 1 (Project Blueprint)** and **Phase 2 (Software Architecture)** are complete enough to start implementation.

However, I want to change what I originally called **Phase 3**.

Most tutorials jump directly into Docker and then coding. For a project like yours, I think that's a mistake.

Instead, **Phase 3 should define the entire domain model**—the language of your application. Once that's done, the database, APIs, and code become much easier to write because everyone (including AI) has a shared understanding of the business concepts.

# PHASE 3 – DOMAIN MODEL & BUSINESS DESIGN

---

# 1. Purpose

The purpose of this phase is to define every entity, its responsibilities, relationships, lifecycle, and business rules before creating the database.

This document is independent of Django, PostgreSQL, or MongoDB. It describes **what the system is**, not how it is implemented.

---

# 2. Domain Overview

The PFMS revolves around a simple idea:

> Every financial event affects one or more assets, and the system continuously verifies that the calculated balances match the balances entered by the user.

Everything in the system supports that objective.

## Purpose

Represents a location where money currently exists.

Examples

```

Wallet

Nabil Bank

Gold
```

An asset is **not** a bank account.

It is simply a place where value exists.

---

### Asset Attributes

```

Description

Status

Created At

Updated At
```

---

## Business Rules

- Asset names must be unique per user.
    
- Opening Balance is set only during creation.
    
- Actual Balance is entered manually.
    
- Calculated Balance is never stored manually.
    
- Assets cannot be deleted if financial transactions reference them.

Business Rules

Difference = 0 → Verified

# 17. Invariants

These conditions must always hold true.

- Every Income has exactly one destination asset.
    
- Every Expense has exactly one source asset.
    
- Every Transfer has one source and one destination asset.
    
- Transaction amounts are always positive.
    
- Categories match transaction type.
    
- All financial operations are atomic.
    
- The Verification Engine is triggered after every financial operation.

# 20. Open Design Questions

Before we write any code, there are a few decisions we should make:

1. **Should assets support multiple currencies in the future?** Even if Version 1 is NPR only, we can design for extensibility.
    
2. **Should transfers allow fees?** For example, transferring money from a bank to a digital wallet might incur a service charge. If so, a transfer could optionally create an associated expense.
    
3. **Should assets be archived instead of deleted?** Archiving preserves historical data and is usually preferable for financial systems.
    
4. **Should reconciliation history be stored?** Instead of only showing the current verification status, we could keep a history of all reconciliation checks to analyze when and why mismatches occurred.
