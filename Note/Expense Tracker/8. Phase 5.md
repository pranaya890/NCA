# 1. API Philosophy

PFMS will expose a **RESTful API**.

The frontend (whether Django templates today or React/Vue/mobile tomorrow) should never access the database directly.

Everything goes through the API.

```text
Browser

↓

REST API

↓

Business Services

↓

Database
```

---

# 2. API Standards

Base URL

```text
/api/v1/
```

Future versions

```text
/api/v2/
```

This allows breaking changes later without affecting existing clients.

Notice something?

There is **no endpoint to update calculated balance**.

Because calculated balance never exists in the database.

# 14. Standard Response Format

Every endpoint should return a consistent structure.

Success:

```json
{
    "success": true,
    "message": "Expense created successfully.",
    "data": {}
}
```

Failure:

```json
{
    "success": false,
    "message": "Validation failed.",
    "errors": {}
}
```

This consistency simplifies frontend development.

---

# 15. Validation Rules

Examples:

**Income**

- Amount > 0
    
- Category must be an income category
    
- Destination asset must exist
    

**Expense**

- Amount > 0
    
- Category must be an expense category
    
- Source asset must exist
    

**Transfer**

- Amount > 0
    
- Source and destination must be different
    
- If negative balances are disabled, ensure sufficient calculated balance before allowing the transfer

# 16. Typical Workflow

Example: User records an expense.

```text
User

↓

Expense Form

↓

POST /api/v1/expenses/

↓

Serializer validates input

↓

Expense Service

↓

Database transaction starts

↓

Expense saved

↓

Financial Engine recalculates balances

↓

Verification Engine compares calculated vs actual

↓

Verification history saved

↓

Dashboard cache refreshed (or marked stale)

↓

Transaction committed

↓

Success response returned
```

# 17. Idempotency

`GET` requests never modify data.

`POST` creates new resources.

`PUT` replaces an existing resource.

`PATCH` (if we use it) updates selected fields.

`DELETE` will be a **soft delete** in Version 1.

# Architectural Improvements Before Coding

Before we move to Docker, I have a few recommendations that will make the project cleaner:

### 1. Balance Check vs Verification

Earlier we discussed `Verification`. I suggest splitting responsibilities:

- **Balance Check**: A manual event where the user enters the actual balance of an asset.
    
- **Verification**: The system's comparison between calculated and actual balances.
    

This distinction mirrors real reconciliation processes and keeps the terminology clear.

---

### 2. Reconciliation Sessions

Instead of only checking one asset at a time, introduce a reconciliation session.

Example:

```text
Reconciliation Session
----------------------
Date: 2026-07-15

Cash
✓ Verified

eSewa
⚠ Difference: Rs. 120

Nabil Bank
✓ Verified
```

This allows users to reconcile all assets together and keeps a history of each session.

---

### 3. Transaction Reference IDs

Every financial transaction should have a unique, human-readable reference, for example:

```text
INC-20260715-0001
EXP-20260715-0008
TRF-20260715-0003
```

These IDs make searching, reporting, and support much easier than relying on database IDs.

---

### 4. Keep Asset Balances Derived

We agreed earlier that calculated balances are derived, not stored. I'd extend that philosophy:

- `initial_balance` is stored.
    
- Transactions are stored.
    
- Balance checks are stored.
    
- Calculated balances are derived by the Financial Engine.
    

That keeps PostgreSQL as the authoritative source of financial history and avoids synchronization bugs.
