# Milestone 2.3 — Custom User Model

This is one of the most important architectural decisions in Django.

## Why create a custom user model now?

Django provides a default `User` model, but changing it **after you've created migrations and started building models** is difficult.

By creating our own user model now, we can later add fields like:

- Profile picture
    
- Preferred currency
    
- Timezone
    
- Theme
    
- Two-factor authentication
    
- Last login IP
    
- Notification preferences
    

without painful migrations.

---

# Step 1: Create `User` model

Open:

```text
apps/users/models.py
```

Replace everything with:

```python
from django.contrib.auth.models import AbstractUser
from django.db import models


class User(AbstractUser):
    """
    Custom user model for the application.
    """

    class Meta:
        db_table = "users"
        verbose_name = "User"
        verbose_name_plural = "Users"

    def __str__(self):
        return self.username
```

This behaves exactly like Django's built-in user model for now, but it's fully customizable.

# Step 2: Create the serializer

In `apps/authentication/serializers.py`:

```python
from django.contrib.auth import authenticate
from rest_framework import serializers


class LoginSerializer(serializers.Serializer):
    username = serializers.CharField()
    password = serializers.CharField(write_only=True)

    def validate(self, attrs):
        username = attrs.get("username")
        password = attrs.get("password")

        user = authenticate(
            username=username,
            password=password,
        )

        if not user:
            raise serializers.ValidationError(
                "Invalid username or password."
            )

        attrs["user"] = user
        return attrs
```

This serializer checks the user's credentials.

---

# Step 3: Create the login view

In `apps/authentication/views.py`:

```python
from rest_framework import status
from rest_framework.response import Response
from rest_framework.views import APIView

from rest_framework_simplejwt.tokens import RefreshToken

from .serializers import LoginSerializer


class LoginView(APIView):

    permission_classes = []

    def post(self, request):

        serializer = LoginSerializer(data=request.data)
        serializer.is_valid(raise_exception=True)

        user = serializer.validated_data["user"]

        refresh = RefreshToken.for_user(user)

        return Response(
            {
                "access": str(refresh.access_token),
                "refresh": str(refresh),
            },
            status=status.HTTP_200_OK,
        )
```

@extend_schema(

class CurrentUserView(GenericAPIView):

        serializer = self.get_serializer(request.user)

# One improvement before we continue

Our login endpoint currently returns raw tokens:

```json
{
    "access": "...",
    "refresh": "..."
}
```

I recommend that **before we implement logout**, we build the shared `core` utilities we planned in Sprint 2:

```
apps/core/
├── responses.py
├── exceptions.py
├── permissions.py
├── pagination.py
├── validators.py
├── utils.py
└── services/
```

Why now?

Because every endpoint we build after this (`me`, `logout`, assets, income, expenses, etc.) can immediately use the same response format and error handling instead of us refactoring dozens of endpoints later.

So here's the order I'd follow:

1. ✅ `GET /api/auth/me/`
    
2. ✅ Build the `core` utilities (shared responses and exception handling)
    
3. ✅ Refactor the authentication endpoints to use them
    
4. ✅ `POST /api/auth/logout/`
    
5. ✅ Add refresh token endpoint (or customize the built-in one)
    

This gives us a clean, reusable architecture before we start implementing the actual financial features.
