---

# 1. Architectural Style

The application will follow a **Modular Monolithic Architecture**.

Why?

- Easier to develop and debug.
    
- Suitable for a single developer.
    
- Faster than microservices.
    
- Easier deployment.
    
- Can later be split into microservices if required.
    

Internally, the project will be divided into independent modules (Django apps) with clear responsibilities.

# 3. Development Philosophy

Every layer should have **one responsibility only**.

For example,

Nginx should never perform business logic.

Django Views should never perform calculations.

Models should not contain complex financial calculations.

Services should not directly generate HTML.

This keeps the system maintainable.

# 10. Financial Calculation Flow

This is the heart of the project.

```
User creates Expense

↓

Serializer validates data

↓

Expense Service

↓

Transaction begins

↓

Expense saved

↓

Balance Verification Service runs

↓

Expected balances recalculated

↓

Verification status updated

↓

Transaction committed

↓

API Response
```

Every financial operation should be executed within a database transaction to prevent partial updates.

# 12. Redis Responsibilities

Redis is **not a database** in this project.

It is used for:

- Celery message broker
    
- Caching dashboard summaries
    
- Session storage (optional)
    
- Temporary locks
    
- Rate limiting (future)
    

---

# 13. Celery Responsibilities

Celery handles tasks that do not need an immediate response.

Examples:

- Rebuilding monthly reports
    
- Refreshing dashboard analytics
    
- Cleaning old logs
    
- Future email notifications
    

Version 1 will use Celery sparingly but the infrastructure will be ready.

# 16. Logging Strategy

Application logs should capture:

- Authentication events
    
- Transaction creation
    
- Transaction updates
    
- Verification failures
    
- Unexpected exceptions
    

Sensitive information such as passwords or tokens must never be logged.

---

# 17. Error Handling

Errors should be returned in a consistent format, for example:

```json
{
  "success": false,
  "message": "Insufficient balance in selected asset.",
  "error_code": "ASSET_BALANCE_NEGATIVE",
  "details": {
    "asset": "Cash"
  }
}
```

Avoid exposing internal stack traces or database details in API responses.

---

# 18. Security Design

- JWT-based authentication
    
- Password hashing with Django defaults
    
- CSRF protection where applicable
    
- Input validation on every endpoint
    
- Authorization checks for every resource
    
- Environment variables for secrets
    
- HTTPS in production
    
- Secure Docker networking
    

---

# 19. Scalability

Although Version 1 targets a single user, the architecture should avoid assumptions that make future expansion difficult.

For example:

- All tables should reference a user.
    
- Services should avoid global state.
    
- API design should support multiple users later.

# 20. Architecture Decisions (ADR)

These are decisions we've made so far:

|Decision|Choice|Reason|
|---|---|---|
|Architecture|Modular Monolith|Simpler than microservices while remaining maintainable|
|Backend|Django + DRF|Mature ecosystem and REST support|
|SQL Database|PostgreSQL|Strong consistency and ACID transactions|
|NoSQL Database|MongoDB|Flexible storage for analytics and logs|
|Cache|Redis|Fast in-memory cache and Celery broker|
|Background Jobs|Celery|Asynchronous task processing|
|Reverse Proxy|Nginx|Standard production deployment|
|Containerization|Docker Compose|Reproducible development environment|
|Financial Data|PostgreSQL only|Critical transactional integrity|
|Analytics Data|MongoDB only|Flexible document storage|

## One Architectural Improvement

I recommend introducing a dedicated **Financial Engine** instead of scattering calculations across modules.

```
                 Income
                    │
                    │
Expense ────────────┼──────────── Transfer
                    │
                    ▼
          Financial Engine Service
                    │
                    ▼
      Balance Verification Engine
                    │
                    ▼
        Dashboard & Reports
```

The Financial Engine becomes the single authority for all calculations. Income, expenses, and transfers don't modify balances directly—they submit events to the Financial Engine, which validates, applies business rules, recalculates expected balances, and triggers verification.

This gives you one place to maintain financial logic, making the application easier to test, extend, and trust. It's a design pattern commonly used in financial software because it keeps critical calculations centralized rather than duplicated across multiple modules.
