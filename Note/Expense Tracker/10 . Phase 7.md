core/

Every other app can safely depend on `core`.

---

# 5. Responsibilities

## models.py

Only define:

- Database schema
    
- Relationships
    
- Constraints (where appropriate)
    
- Simple helper methods (e.g., `__str__`)
    

Avoid complex calculations or business rules here.

---

## serializers.py

Responsibilities:

- Validate incoming data
    
- Transform request/response payloads
    
- Never perform financial calculations
    

---

## views.py

Responsibilities:

- Receive requests
    
- Authenticate users
    
- Authorize access
    
- Call services
    
- Return responses
    

Views should be as thin as possible.

---

## services.py

This is the heart of each app.

Every business operation belongs here.

Examples:

```text
create_income()

update_income()

delete_income()

create_expense()

create_transfer()
```

Services coordinate transactions and call other services when needed.

---

## selectors.py

Selectors are responsible for read-only queries.

Examples:

```text
get_dashboard_summary()

get_asset_history()

get_monthly_income()

get_recent_expenses()
```

Keeping read logic separate from write logic improves clarity and testing.

---

## validators.py

Contains domain-specific validation.

Examples:

- Transfer source and destination must differ.
    
- Category type must match transaction type.
    
- Negative balances not allowed for certain asset types.
    

---

## permissions.py

Contains custom permission classes for DRF.

Even though Version 1 is single-user, implement permissions correctly from the start.

---

## tasks.py

Contains Celery tasks.

Examples:

- Refresh analytics
    
- Generate reports
    
- Clean logs
    

Tasks should call services rather than duplicate business logic.

---

## signals.py

Use signals sparingly.

Only for cross-cutting concerns such as logging or cache invalidation.

Do **not** rely on signals for financial calculations.

---

# 6. Dependency Flow

The application should follow this direction:

```text
HTTP Request
      │
      ▼
View
      │
      ▼
Serializer
      │
      ▼
Service
      │
      ▼
Model
      │
      ▼
Database
```

For reads:

```text
HTTP Request
      │
      ▼
View
      │
      ▼
Selector
      │
      ▼
Database
```

Services should not call views. Models should not depend on serializers.

---

# 7. The Financial Engine

Instead of scattering calculations, create a dedicated component within `core/services`.

Example:

```text
core/services/

financial_engine.py
```

Responsibilities:

- Calculate expected balances.
    
- Apply business rules.
    
- Trigger verification.
    
- Provide reusable calculation methods.
    

Every income, expense, and transfer service should use the Financial Engine.

---

# 8. Verification Service

Also in `core/services`:

```text
verification_service.py
```

Responsibilities:

- Compare calculated vs. actual balances.
    
- Generate reconciliation records.
    
- Produce verification status.
    

This keeps reconciliation logic centralized.

---

# 9. Query Philosophy

Separate reads from writes.

**Selectors** perform queries.

**Services** perform modifications.

Example:

```text
ExpenseView
    │
    ├── GET  → ExpenseSelector
    └── POST → ExpenseService
```

---

# 10. Transactions

Every financial write operation must use a database transaction.

Example:

```python
with transaction.atomic():
    create_expense()
    recalculate_balance()
    create_verification_record()
```

If anything fails, the entire operation rolls back.

---

# 11. Exceptions

Create custom exceptions in `core/exceptions.py`.

Examples:

```text
InsufficientBalanceError

InvalidCategoryError

VerificationError

AssetNotFoundError

DuplicateAssetError
```

Views should convert these into standardized API responses.

---

# 12. API Responses

Use helper functions in `core/responses.py`.

Example structure:

```json
{
  "success": true,
  "message": "Expense created successfully.",
  "data": {}
}
```

This keeps responses consistent across all endpoints.

---

# 13. Constants

Avoid hardcoding strings.

Store shared values in `core/constants.py`.

Examples:

- Asset types
    
- Verification statuses
    
- Transaction reference prefixes
    

---

# 14. Testing Strategy

Every app should include:

- Model tests
    
- Service tests
    
- API tests
    
- Permission tests
    

Prioritize testing services because they contain the business logic.

---

# 15. Logging

Application events should be logged consistently.

Examples:

- User login
    
- Income created
    
- Expense updated
    
- Transfer deleted
    
- Verification mismatch
    

Logging should happen through a shared logging service or utility.

# 16. Coding Standards

- Follow PEP 8.
    
- Use type hints.
    
- Write docstrings for public functions.
    
- Keep functions small and focused.
    
- Avoid duplicate code.
    
- Prefer composition over inheritance.

# 18. Future-Proofing

Even though Version 1 is single-user:

- Every model should have a `user` foreign key where appropriate.
    
- Avoid global assumptions.
    
- Design APIs that can support multiple users later.

# 19. Things We Will Not Use (Initially)

To keep the project focused, we will avoid:

- Django signals for core business logic.
    
- Generic CRUD views for financial modules (custom views give more control).
    
- Third-party service-layer libraries.
    
- Repository pattern (selectors already provide separation).
    
- GraphQL.
    
- Microservices.
    

These can be introduced later if needed.

---

# 20. Backend Development Rules (Mandatory)

These are non-negotiable rules for the project:

1. No business logic in views.
    
2. No business logic in serializers.
    
3. No financial calculations in models.
    
4. No duplicated calculation logic.
    
5. All financial writes use `transaction.atomic()`.
    
6. Every financial operation goes through the Financial Engine.
    
7. Every financial write triggers verification.
    
8. Read operations use selectors.
    
9. Write operations use services.
    
10. Use custom exceptions for business rule violations.
    
11. Never store calculated balances in PostgreSQL.
    
12. Never store financial transactions in MongoDB.
    
13. Never bypass the service layer.

# My Final Architectural Recommendation

I'd like to introduce one more concept that I believe will make the project significantly cleaner without making it more complicated:

## Add a `TransactionReferenceService`

Every financial transaction (income, expense, transfer) should receive a unique, readable reference generated by a shared service.

Examples:

```text
INC-20260715-000001
EXP-20260715-000001
TRF-20260715-000001
```

Benefits:

- Easier debugging.
    
- Better audit trails.
    
- More professional reports.
    
- Users can search by reference.
    
- Stable identifiers independent of database IDs.
    

This is a small addition but gives the system a much more polished feel.
