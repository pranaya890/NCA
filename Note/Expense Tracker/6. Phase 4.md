# 23. One Major Architectural Change I'd Recommend

## ❌ Current Design

```
Income

↓

Updates Asset Balance

↓

Expense

↓

Updates Asset Balance
```

This seems simple, but it creates synchronization risks.

---

## ✅ Recommended Design

Instead, treat **Asset.actual_balance** as something the user reports, not something the system modifies.

The system calculates balances dynamically:

```
Opening Balance

+

Income

-

Expenses

+

Incoming Transfers

-

Outgoing Transfers

=

Calculated Balance
```

The **Calculated Balance** is never stored in the database. It is computed whenever needed or cached temporarily.

Then compare it against the **Actual Balance** entered by the user.

This has several advantages:

- You never have to worry about balances drifting because of a bug.
    
- Financial calculations are always reproducible from transaction history.
    
- Reports remain consistent even if old transactions are edited.
    
- The system naturally supports reconciliation, which is your project's core purpose.
    

The only balance stored permanently is the user's **Actual Balance**, because that represents the real-world value you're trying to reconcile against the calculated value.

## Before Phase 5

I have **one significant recommendation** that will improve the architecture further.

Right now, we have separate `income`, `expense`, and `transfers` tables. That's easy to understand, but many accounting systems instead use a unified **ledger** model where every financial event is a transaction with one or more entries.

For Version 1, keeping separate tables is perfectly reasonable and easier to learn.

However, if your long-term goal is to build something approaching professional accounting software, I would eventually migrate to a **ledger architecture**. It is more complex initially but scales much better and naturally supports reconciliation, auditing, and advanced financial features.

My suggestion is:

- **Version 1:** Separate `income`, `expense`, and `transfers` tables (simpler, educational, faster to build).
    
- **Version 2:** Introduce a unified ledger while keeping the public interface unchanged.
    

This gives you the best balance between learning, maintainability, and future growth.
